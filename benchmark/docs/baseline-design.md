# Baseline v1 设计稿

日期：2026-10-29。状态：实现与首次验证；本稿预先确定比较规则，实测成绩写在独立 runs 目录。

## 1. 问题与实验目标

输入一段完整公开多会话聊天历史和一个用户问题，输出前 k 条会话记忆及其消息上下文。第一版只评记录/证据检索，不加入生成回答和 LLM 裁判。

需要回答：

1. 当前项目在固定题目上能否找到发布数据标出的相关会话？
2. search 返回的锚点经 get_details 展开后，是否真正交付标注证据？
3. 为此返回了多少字符、花费多少查询时间与建库时间？
4. 相比简单词面检索，当前整套向量检索流程在哪些题上不同？

这是一个**完整方案对照**。由于 BM25 和当前项目的切片、打分和锚点筛选不同，本实验不能把分差全部归因于 embedding 模型。纯组件贡献需另外做固定其余条件的消融。

## 2. 数据与标注

使用 [LoCoMo 官方仓库](https://github.com/snap-research/locomo)中固定提交的 `locomo10.json`，保留许可证、原文件、下载来源和 SHA256。

第一版演练使用 dev 中固定一段完整 conversation，其所有 session 都参与检索，不预先只挑含答案的 session。每个 session 对应一条 chat_event，每个 dia_id 对应一条原消息。

仅将原始时间、会话标题、说话人和消息文字提供给检索器。源数据中的 QA、answer、evidence、生成式 observation/summary 不进入索引。图像不下载；有图像证据的题保守排除。

demo 选择24道有效单跳开发题。完整转换版保留可完整映射的单跳、多跳、时间题，按场景固定分为 dev/test。开放域与对抗题不强行转换成有答案检索题，排除数量记录在数据 manifest。

发布数据的多个 evidence 不一定构成唯一或最小充分证据集合。本版的证据指标因此明确叫“发布标注证据覆盖”，不能把未标出的等价来源一律认定为无用，也不能等同于答案正确率。

## 3. 两个 baseline 的定义

| 项目 | B0：BM25 词面检索 | B1：当前项目真实向量检索 |
| --- | --- | --- |
| 主要作用 | 简单、可解释的对照 | 固定当前实现，作为后续版本比较起点 |
| 可见信息 | 标题、原始消息 role/content | 同样的标题、原始消息 role/content |
| 编码/打分 | Okapi BM25；k1=1.5，b=0.75 | 项目当前配置的真实本地 BGE-M3、归一化向量和 FAISS |
| 检索单元 | 标题与完整单条消息，不截断 | 项目实际主字段、字段记录、按token切分的消息 |
| 主记录聚合 | 标题/消息最高分 | 当前主向量与子记录的最高相似度 |
| 消息锚点 | 正分消息按名次选取，遵守间距 | 当前余弦分差、名次和间距规则 |
| 上下文展开 | 相同的前后消息半径 | 实际 get_details_by_ids 展开 |

BM25 的词法切分为英文小写词/数字与逐个CJK字，不做词干化和停用词过滤。它针对英语 demo 是合理的简单起点；以后评中文时，应固定并对比更适当的中文词法处理。

BM25分数与余弦分数没有同一尺度，因此不能把项目的0.2余弦分差直接套到BM25。两种锚点规则的差异会写入每次报告。主记录指标可比较两个完整方案，证据层差异还受锚点策略影响。

BM25的非负平滑IDF为 `log(1 + (N-df+0.5)/(df+0.5))`；与常见Okapi变体一致。本实现对query词去重，避免把不同实现的BM25当作完全相同基线。

## 4. 固定条件

- 固定原始文件、标准化语料、查询、标注和场景范围；检索器不能搜索其他人物场景。
- 固定 k=5、最多3条代表消息、前后各10条消息；同一k不保证同一返回字符预算。
- 固定当前模型、CPU设备和源码，保存实际源文件哈希，包括未提交修改。
- 使用独立子进程与每run的独立DB/索引，不连接正式记忆库或已有data-test副本。
- 建库使用整个演练语料，一次同步创建；不将每次save触发后台重建的耗时混入查询延迟。
- 每方案每场景预热一次；单次查询计时含该适配器检索与正文展开，模型加载和建库单列。
- 先运行dev。test用于方案稳定后的版本验证，按场景分组避免同一事实改写跨集合。

当前两个完整方案的计时边界不同：BM25在内存中查找；项目使用真实search中的FAISS读取、SQLite回源、query embedding和详情展开，还经过子进程请求响应。报告保留实际worker内部延迟；不要仅凭延迟差值归因于检索算法。

## 5. 指标与失败处理

| 指标 | 定义 | 解释边界 |
| --- | --- | --- |
| Hit@k | 前k条去重主记忆是否有任意标注相关项 | 找到一条不代表证据齐全 |
| Recall@k | 找回的标注相关主记忆 / 全部标注相关主记忆 | 针对发布标注，不保证相关性穷尽 |
| MRR@k | 第一条相关项的倒数排名，未找到记0；逐题平均 | 只看第一条正确项 |
| 标注证据覆盖 | 交付的证据组 / 该题全部标注证据组 | 每组任意等价备选命中即覆盖 |
| 全部标注证据覆盖率 | 所有证据组都交付的题目比例 | 不是最终问答准确率 |
| 返回字符数 | 返回消息content的Unicode字符数 | 不是token数，也不是MCP整个响应字节数 |
| p50/p95延迟 | 查询样本的nearest-rank分位数 | 小样本描述，不是生产SLA |

消息ID只在原会话内唯一，证据必须匹配 `(record_id, message_id)`。只返回候选的消息ID不算交付；必须出现在实际返回正文中。

运行异常的有答案题质量计0，并单列错误率。无答案题不加入无定义的Recall/证据分母；当前数据转换未提供无答案评测，不能声称系统会拒绝不存在的记忆。

本版不把质量、延迟、字符量加权成一个总分，先保留各自含义。

## 6. 产物与复现

每次创建新的run_id并保留：

1. 数据集、实际查询集合和源码/配置指纹；本机Python和设备信息。
2. 项目源码与配置快照、模型指纹、实际向量数。
3. 每题排名、分数、代表消息、返回正文、延迟及错误。
4. 每题分数、按类别汇总和失败案例。
5. Markdown与HTML报告，以及机器可读JSON。

比较两次运行必须核对数据与实际查询集合一致，k一致。改变题目、过滤样本、重切分数据后，应创建新评测版本；不能沿用旧成绩直接宣称提升。

## 7. 后续消融怎么设计

先看失败案例，再选择一个有理由的实验：

- 固定主记录候选与锚点，只替换上下文展开方式，观察证据/字符的变化。
- 固定原始信息和聚合逻辑，比较消息粒度与token切片粒度。
- 固定切片和打分，比较最大分与其他主记录聚合策略。
- 在加入中文题和无答案题后，仅用开发集选择词法规则或过滤阈值。

当前 `returnMessageNum` 同时控制消息锚点间距和展开半径。直接修改 `--window-radius` 是一个复合配置实验，不能当成只改变展开长度的干净消融。

## 8. 设计稿参考

- [LongMemEval 的 Memory Retrieval](https://github.com/xiaowu0162/LongMemEval#memory-retrieval)：参考以不同粒度和BM25/向量方法组织对照。数据集和协议与本项目不同，成绩不作横向比较。
- [Introduction to Information Retrieval，第8章](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-in-information-retrieval-1.html)：测试集合、相关性与排序指标。
- [Okapi BM25 原理](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html)：词频、逆文档频率与长度归一化。

可以复用本稿结构：**问题 → 数据/标注 → 基线定义 → 固定条件 → 指标/异常 → 产物 → 消融与结论边界**。
