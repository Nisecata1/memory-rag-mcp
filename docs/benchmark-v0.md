# memory-rag-mcp：评估基础与第一轮 benchmark 方案

编写日期：2026-10-28。

本文基于当前代码与接口文档的静态审阅。它是学习材料和拟实施的实验方案，不代表已经建立题集、运行真实 embedding 评测或取得下述任何成绩。当前尚无可报告的检索质量分数。本次没有读取正式记忆库正文，也没有修改服务、配置或既有测试。

## 1. 先明确这个项目在评什么

本项目负责保存结构化记忆、寻找候选记忆、定位聊天消息并展开上下文。最终自然语言回答由调用它的 AI 完成，服务本体没有回答生成器。

第一阶段的任务定义可以写成：

> 给定固定版本的历史记忆和一个用户查询，在有限返回文本量与可接受延迟下，找回能够支持查询的原始记录与必要证据。

需要分开观察两道关：

1. **主记录检索**：正确的 fact、project_record、project_registry 或 chat_event 是否进入前 k 条。
2. **证据交付**：调用详情接口后，真正需要的事实或消息是否进入返回正文。

找对一场长对话，但最终只返回了没有关键事实的片段，第一关可以成功，第二关仍然失败。相反，返回全文可能覆盖证据，但需要报告它多返回了多少文本。

以后如果加入回答生成，才增加答案正确性、证据忠实性、引用支持和拒答质量等下游指标。必须固定回答模型和提示词，才能判断检索改动对最终回答的影响。

## 2. 五个容易混淆的词

| 名词 | 含义 | 在本项目中的例子 |
| --- | --- | --- |
| Dataset，数据集 | 实验使用的数据 | 一份冻结的记忆语料与一组查询 |
| Ground truth，人工标注 | 什么结果算对 | 某查询对应的主记忆 ID、消息 ID 与必要事实 |
| Metric，指标 | 计算表现的规则 | Hit@5、MRR@5、证据覆盖率、延迟 |
| Baseline，基线 | 用来比较的起点方案 | 当前版本；或信息可见范围相同的 BM25 方案 |
| Benchmark，评测基准 | 固定任务、数据、标注、指标和运行协议的一整套考法 | Memory Retrieval v0；固定语料快照、查询、标注和参数，再比较方案 |

Ragas 是实现部分评估的工具，不是题目和标准本身。安装工具不能替代设计数据集、相关性标注与公平比较。

## 3. 当前代码已经做了什么

以下是实现事实，尚不能直接当作效果或性能优势：

| 已实现机制 | 代码或契约位置 | 值得检验的假设 |
| --- | --- | --- |
| 按类型存储记忆，SQLite 保存主数据 | README.md；server_utils.py | 更新、删除后检索结果与主数据一致 |
| 主记忆文本之外，派生字段记录及聊天消息切片 | server_utils.py:2635、3018 | 小粒度检索是否减少长记录中的信息遗漏 |
| 本地 BGE-M3；归一化向量；FAISS Flat-IP | config/settings.yaml:27；embedding_utils.py:30；server_utils.py:3917 | 在真实改写查询中是否优于词面匹配 |
| 主记忆分数取其主向量与子向量命中的最大分 | server.py:319；docs/retrieval-api.md:60 | 最大分聚合是否提高召回；长记录是否更容易偶然高分，需要实验验证 |
| 每条聊天选择代表消息，再按锚点展开上下文 | server_utils.py:1863、1894 | 是否能用较少文本交付关键证据 |
| embedding 缓存与增量刷新 | README.md；server_utils.py | 修改一小部分内容时，实际编码量与更新时间是否减少 |

当前配置还意味着：

- `min_similarity=null`：默认不按最低相似度过滤；没有相关记忆的查询仍可能返回候选。返回候选不等于服务声称存在答案。
- `message_top_k=3`：每条聊天最多选择三个代表消息，不是全库只返回三条消息。
- `returnMessageNum=10`：每个锚点前后各展开十条消息；这不是 token 上限，也不是十轮问答。
- `top_k=5` 只限制最终主记忆数量。`server.py:248` 当前搜索全部向量，再回源并折叠，不能由 top_k 很小推断检索开销很小。
- 只传主 ID 读取聊天详情，得到的是尾部预览；需要按主 ID 传回搜索结果中的消息锚点，才能展开命中附近内容。
- 主排序依据相似度，没有显式时间过滤、时间衰减或新旧事实冲突消解。存有时间字段不等于已经具备这些能力。

## 4. 功能测试和质量评测回答不同的问题

现有测试覆盖接口规则、消息窗口、索引一致性、并发写入等。这些测试应当保留。

例如 `tests/test_chat_event.py:18` 的 RecordingEmbedder 以 SHA256 字节构造伪向量；`tests/test_dialogue_context.py:422` 的 FakeIndex 使用预设排名。它们适合验证流程有没有按约定工作，不用于证明真实语义检索是否准确。

因此需要并行保留两套验证：

- **回归测试**：代码变更有没有破坏约定。
- **检索 benchmark**：在相同题目与条件下，用户需要的信息能否更好地找回。

## 5. 第一轮如何出题

### 5.1 先建立一个小型演练集，再制作正式 v0

先手工构造约十道教学题，把标注、运行和评分走通。教学题不用于宣传真实使用效果。

随后从实际使用需求中制作约六十道 v0 查询，作为起步规模，而非充分统计保证。可以先按下表均衡取样，再根据真实使用比例调整；同时报告各类结果。

| 类型 | 检查什么 |
| --- | --- |
| 精确事实或术语 | 名称、数字、错误信息能否找回 |
| 同义改写 | 不沿用原文关键词时还能否找到 |
| 相似主题干扰 | 能否区分两个相似项目或不同事件 |
| 长对话与多处证据 | 中部细节是否丢失；是否覆盖多个必要事实 |
| 时间与知识更新 | 是否交付最新状态及其修订依据，而非只有旧说法 |
| 确实没有记录 | 是否返回低相关候选；阈值能否过滤，同时不过多过滤有效查询 |

约三十道作为开发题，另外三十道封存为测试题。按相同事件、原始对话或问题来源分组划分，尽量让同一事实的多个改写留在同一组，避免开发题和测试题只是换一种问法。

小样本用来找明显问题。三十道测试题中，一题就约占 3.3 个百分点，不能把一两题的变化宣称为稳定优势。后续扩大题集，并报告配对差异和不确定性。

### 5.2 固定语料和标注

为每个评测版本固定：

- 语料快照及哈希，保留记录和消息的稳定 ID。
- 查询集版本、开发/测试划分与人工标注。
- 代码版本；如工作区有未提交修改，另外保存补丁摘要或源码哈希。
- 模型版本或本地模型指纹、切片规则与配置。

标准证据标在**主记忆 ID + 消息 ID 或正文范围**上，不绑死内部 `fmem-*` 切片 ID。切片方法改变时，原文证据仍应保持相同。

对于一个必要事实存在多处等价证据的情况，把它们标成一组备选证据；命中任意一处即可覆盖该事实。若需要两个不同事实才能完成任务，应设成两个必要证据组。

评测问题和人工参考答案不要回写入检索库。原始记忆本身包含答案是正常的，评测就是要检查能否找到；把专门整理好的测试问答对写进去，会改变考法。

### 5.3 一条标注长什么样

下面仅是格式演示，ID 和内容均为虚构，并不是本次读取的私人记录：

```json
{
  "query_id": "demo-q001",
  "split": "demo",
  "category": "temporal_update",
  "query": "演示项目现在把服务部署在哪台机器？",
  "answerable": true,
  "as_of": "2026-10-28T12:00:00+08:00",
  "relevant_record_ids": ["demo-event-01"],
  "evidence_groups": [
    {
      "group_id": "current_host",
      "alternatives": [
        {
          "record_id": "demo-event-01",
          "message_id": "demo-msg-18",
          "required_text": "已从演示机器A迁移到演示机器B"
        }
      ]
    }
  ],
  "reference_note": "应找回迁移后的状态；只找到早期部署说明不够。"
}
```

真实标注时需要核对整个冻结语料是否存在其他等价证据，不能把未标到的正确来源自动视为错误。`reference_note` 只帮助人工评分，不参与检索。

`as_of` 是题目判断时点，不是声称当前接口已支持日期参数；需要在查询文本或独立实验协议中明确表达时间条件。

## 6. 第一版指标

### 6.1 主记录层

- **Hit@k**：前 k 条主记忆中是否至少有一条相关记录。每道题是 0 或 1，最终取平均。
- **Recall@k**：前 k 条中找回的已标注相关主记忆数，除以该题全部已标注相关主记忆数。逐题计算后再平均。相关性标注不全时，必须说明它只是针对已知标注的召回率。
- **MRR@k**：第一条相关记录若排在第 r 位，该题得 1/r；前 k 没有相关记录则得 0，最后取平均。

例如一题有三条相关主记忆，前五条找回两条，第一条相关结果排第二：该题 Hit@5=1，Recall@5=2/3，RR@5=1/2。Hit 并不等于证据齐全。

无答案题不并入上述需要相关记录的均值，单独报告。并列分数使用预先固定的打破平局规则。

### 6.2 最终交付的证据层

运行链路必须是：

`查询 → search → 按主 ID 传回 matched_message_ids → get_details_by_ids → 检查返回原文`

- **证据覆盖率**：最终返回文本覆盖的必要证据组数 / 全部必要证据组数，再逐题平均。
- **完整证据成功率**：该题所有必要证据组是否均被覆盖，再逐题平均。
- **条件证据覆盖率**：按必要证据组计算，仅在该组至少一个备选证据所属的主记录进入候选时，观察该组证据是否交付。另报“全部必要证据组均有候选主记录”的题目比例，避免把多记录题中漏掉另一条主记录误归因于窗口。不同方案进入条件统计的子集可能不同，不能直接用条件分数宣称优劣；主成绩仍报告无条件的端到端证据覆盖。
- **返回文本量**：同时记录实际 JSON 响应字节数，以及固定 tokenizer 下的 token 数；若暂时只统计字符，明确叫字符数，不能写成 token 数。

对聊天，需要包含消息中的必要原文范围，不能只因为轻量返回了消息 ID 就算已经交付证据。对 fact/project 等类型，检查返回正文对应的事实或文本范围。

锚点本身未直接命中目标消息，但其展开窗口覆盖了证据，证据交付仍可算成功；锚点命中只是额外诊断项。

无答案题没有必要证据组，不并入证据覆盖指标。有答案题发生运行错误时，无条件端到端证据覆盖记 0，同时单列错误率，不能剔除故障请求后只报告成功请求的成绩。

### 6.3 无答案题与运行状态

本阶段服务只返回候选，不代替用户回答“有/没有”。先观察无答案题的分数分布、返回候选数量与人工相关性。

如需测试相似度阈值，只用开发集选择，固定后在测试集同时报告：

- 无答案题中仍返回候选的比例。
- 有答案题中被过滤为空的比例。
- 阈值下的主记录和证据覆盖成绩。

这些是检索过滤行为，不等于最终 AI 的拒答准确率。服务不可用、索引重建中、索引校验失败应单独计为运行错误，不能当作正确地返回“无记录”。

### 6.4 性能与增量更新

第一轮分别记录冷启动、模型已加载后的查询 embedding、检索与回源、详情展开以及整体延迟。预热后重复运行，报告 p50/p95、查询次数、CPU/内存环境与是否并发。

规模至少同时记录：主记忆数、消息数、实际向量数和索引体积。几条很长的对话也可能产生很多向量。

若验证增量更新，另外记录新增/改写/删除一小条记录时的编码条数、编码 token 数、更新时间、峰值资源及更新后检索一致性。这属于另一组实验，不和查询质量混成一个总分。

## 7. 第一轮如何比较方案

首先冻结当前实现，作为可复现的 B0。不要先改一轮再把旧版叫作基线。

| 实验 | 主要回答什么 | 比较条件 |
| --- | --- | --- |
| 当前实现 B0 | 目前到底表现如何 | 保存全部配置与逐题结果 |
| BM25 词面基线 | 语义向量是否带来额外价值 | 使用相同可见原始信息、检索单元与输出粒度；固定中文分词或字符切分规则 |
| 关闭某类字段/消息索引的消融 | 某种索引信息是否有贡献 | 每次只改一类，明确可见信息是否也减少 |
| 固定 search 结果，对比尾部预览与锚点展开 | 定位机制是否交付更多关键证据 | 使用相同候选主记录；报告证据覆盖与实际文本量 |
| 固定锚点，再改变展开窗口 | 邻近上下文要多大才合适 | 同一组锚点，分别比较覆盖率与文本量 |

三个特别容易混淆的地方：

1. **摘要-only 与摘要加原文比较**同时改变了可见信息，不能把所有提升都归因于“切块粒度更好”。
2. 当前 `returnMessageNum` 同时控制代表消息间距与详情展开半径。直接改配置会改变两个环节；纯窗口实验应先固定已选锚点，再改变展开规则。
3. BM25 与向量方案需要合理的中文切分规则；只按空格拆中文会制造过弱基线。完整方案比较与单组件消融应分别命名、解释。

相同 k 不代表相同上下文预算。第一轮可先报告“原生行为下的质量—文本量”；之后再定义确定性的 token 截断/装箱规则，在同一预算下比较。全文读取可以做诊断参照，但不能把它在无限文本预算下的覆盖成绩当作公平胜出。

## 8. 逐题结果和第一轮验收

每个方案每道题至少保存：

```text
run_id / query_id / corpus_version / config_hash
ranked_record_ids / scores
selected_message_ids / actually_returned_message_ids
covered_evidence_group_ids
response_bytes / response_tokens
latency_breakdown / runtime_status
failure_reason / human_note
```

失败原因建议先用这些类别：

- 正确主记录未进入 top-k。
- 主记录已找到，但代表消息或展开窗口漏掉证据。
- 只交付旧状态，没有交付更新依据。
- 无相关记录，但返回低相关候选。
- 返回文本过多。
- 超时或服务/索引不可用。
- 人工题目或标注需要修订。

第一轮结束时应得到：

1. 冻结的语料和标注，而不是临时手选几个成功案例。
2. 当前实现的逐题基线结果。
3. 一张按题型拆分的结果表，含证据覆盖、文本量、延迟和错误数。
4. 至少五个有原文依据的失败案例。
5. 根据失败占比提出的一个改动，以及保持其余条件固定的复测。

## 9. 读什么，以及什么时候读

1. **现在先读检索评估基础**：[Introduction to Information Retrieval，第 8 章](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-in-information-retrieval-1.html)。重点是测试集合、相关性标注和排序指标。它出版较早，但这些基础正是本项目目前缺少的评估骨架。
2. **随后读记忆任务设计**：[LongMemEval 官方仓库](https://github.com/xiaowu0162/LongMemEval)及其论文。重点看信息提取、跨会话、时间、知识更新、无答案等任务及证据标注。它的 `answer_session_ids` 标记证据会话，`has_answer` 标记证据消息，并提供会话/消息粒度的检索实验和 BM25 等基线，和本项目两级评估直接相关。官方完整任务还包含回答模型；只抽取其检索部分时，必须标明这是检索子任务，不把检索命中率冒充官方回答准确率。其官方检索统计排除没有答案位置的无答案题；本地无答案过滤诊断需单独说明。接入时固定具体数据版本与协议。
3. **增加回答生成后再读**：[Ragas Faithfulness](https://docs.ragas.io/en/stable/concepts/metrics/available_metrics/faithfulness/)和[RAGChecker](https://github.com/amazon-science/RAGChecker)。理解答案是否受证据支持，以及检索和生成如何分开诊断。LLM 裁判需要人工抽检校准，其打分不是绝对真值。

公开 benchmark 有助于可复现比较，但不能代替中文个人项目记忆的实际查询。先把项目自己的 v0 做完整，再接一个公开数据集，清楚区分两者的结论范围。
